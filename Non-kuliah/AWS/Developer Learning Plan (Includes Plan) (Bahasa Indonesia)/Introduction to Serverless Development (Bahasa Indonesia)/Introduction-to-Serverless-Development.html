TL;DR

  • Nirserver (serverless) = Anda menulis fungsi; penyedia mengurus server, penskalaan, dan ketersediaan.
  • Modelnya event-driven: sesuatu terjadi → fungsi dijalankan. Bayar per pemakaian, bukan per server menganggur.
  • Inti AWS: Lambda (kode), API Gateway (HTTP), DynamoDB (data), S3/SNS/SQS (event).
  • Fungsi Lambda harus stateless; status disimpan di layanan eksternal.
  • Dikelola sebagai infrastruktur-sebagai-kode: SAM / Serverless Framework / CDK; diuji lokal, di-log via CloudWatch.

Konsep inti

Apa itu pengembangan nirserver

Nirserver (serverless) adalah model di mana Anda hanya menulis dan mengunggah kode fungsi; penyedia cloud mengurus server, penskalaan, penambalan, dan ketersediaan. Server tetap ada — Anda hanya tidak mengelolanya.

Penting karena beban operasional dan biaya infrastruktur menganggur hilang: Anda membayar saat kode benar-benar berjalan.

Miskonsepsi: "tanpa server" berarti tanpa server. Server tetap ada; yang hilang adalah pekerjaan mengelolanya.

Memulai secara serverless

Model mentalnya event-driven: sebuah kejadian (permintaan HTTP, unggahan berkas, pesan antrean, jadwal) memicu fungsi yang singkat dan terfokus. Rangkaian layanan khas AWS:

  • AWS Lambda — menjalankan kode fungsi.
  • Amazon API Gateway — pintu HTTP/REST ke Lambda.
  • Amazon DynamoDB — basis data nirserver.
  • Amazon S3, SNS, SQS, EventBridge — sumber event.

Penting karena Anda merangkai layanan terkelola alih-alih mengoperasikan satu server tunggal yang menanggung semuanya.

Menulis fungsi Lambda

Fungsi Lambda punya satu titik masuk (handler) yang menerima dua argumen: event (data pemicu) dan context (informasi runtime). Runtime populer: Python, Node.js, Java, Go, .NET.

Hal kunci: fungsi harus stateless. Tiap pemanggilan bisa berjalan di lingkungan berbeda, jadi status harus disimpan di layanan luar (DynamoDB, S3). Anda juga mengatur memori, waktu tunggu (timeout), dan peran IAM yang menentukan izin fungsi.

Miskonsepsi: variabel global di fungsi aman disimpan. Bisa saja dipakai-ulang, tetapi tidak dijamin — jangan andalkan status antar pemanggilan.

Mengelola aplikasi nirserver

Aplikasi nirserver jarang satu fungsi; biasanya banyak fungsi + API + tabel + izin. Semuanya dikelola sebagai infrastruktur-sebagai-kode: AWS SAM, Serverless Framework, atau AWS CDK.

Konsep pengelolaan penting: versioning dan alias (mengarahkan trafik ke versi tertentu), environment variable, konfigurasi per tahap (dev/prod), serta pipeline CI/CD. Deployment menjadi dapat diulang, bukan klik manual di konsol.

Pengujian dan debugging

Uji lokal dengan SAM CLI (sam local invoke) untuk menjalankan fungsi di mesin sendiri. Uji unit dengan memanggil handler langsung dan menyuplai objek event buatan.

Di produksi, jejaknya lewat Amazon CloudWatch Logs (pesan print/console.log) dan AWS X-Ray untuk melacak alur antar-layanan. Perhatikan pula cold start: pemanggilan pertama setelah lama menganggur terasa lebih lambat.

Miskonsepsi: bug bisa di-debug dengan breakpoint seperti aplikasi biasa. Di cloud, debugging berbasis log dan trace, bukan menempelkan debugger ke proses.

Kode

Handler Lambda (Python): event membawa data pemicu, nilai balik dibungkus sebagai respons.

import json

def lambda_handler(event, context):
    name = event.get("name", "dunia")
    return {
        "statusCode": 200,
        "body": json.dumps({"pesan": f"Halo, {name}!"}),
    }

Definisi infrastruktur dengan AWS SAM (YAML): fungsi + endpoint API dalam satu berkas.

AWSTemplateFormatVersion: "2010-09-09"
Transform: AWS::Serverless-2016-10-31
Resources:
  FungsiHalo:
    Type: AWS::Serverless::Function
    Properties:
      Handler: app.lambda_handler
      Runtime: python3.12
      Events:
        Api:
          Type: Api
          Properties:
            Path: /halo
            Method: get

Alur kerja SAM:

sam build                 # bangun artefak
sam local invoke FungsiHalo -e event.json   # uji di lokal
sam deploy --guided       # deploy ke AWS

Apa yang berubah kalau X diubah: menambah nilai Timeout memberi ruang proses lebih lama, tetapi biaya ikut naik dan batas maksimum platform tetap berlaku.

Latihan mandiri

1. Kenapa fungsi Lambda harus stateless, dan di mana status sebaiknya disimpan?

Lihat jawaban

Karena pemanggilan bisa berjalan di lingkungan/instance berbeda, sehingga variabel lokal tak terjamin bertahan. Status disimpan di layanan luar seperti DynamoDB atau S3.

2. Apa beda event dan context pada handler Lambda?

Lihat jawaban

event = data pemicu (mis. isi permintaan HTTP atau unggahan S3). context = informasi runtime (nama fungsi, sisa waktu, identitas pemanggil).

3. Kapan serverless kurang cocok dipakai?

Lihat jawaban

Untuk beban berat yang merata terus-menerus atau komputasi panjang, di mana server/VM tetap lebih murah dan sesuai; serverless paling untung saat trafik naik-turun dan tugas singkat.

4. Bagaimana cara men-debug aplikasi nirserver di produksi?

Lihat jawaban

Lewat CloudWatch Logs (jejak cetak) dan AWS X-Ray (trace alur antar-layanan), bukan dengan menempelkan debugger ke proses.

Jebakan & FAQ

Apakah serverless benar-benar tanpa server? Bukan. Server ada, tetapi dikelola penyedia; Anda hanya mengurus kode.

Apakah bayar selalu lebih murah? Tidak selalu. Untuk beban berat yang merata, server/VM bisa lebih murah; serverless unggul saat pemakaian naik-turun.

Apa itu cold start? Keterlambatan saat fungsi dipanggil pertama kali setelah lama menganggur, karena runtime perlu disiapkan.

Bisakah fungsi Lambda menyimpan file permanen? Tidak andal — penyimpanan sementara bersifat sementara. Simpan ke S3/DynamoDB.

Perlu izin apa agar Lambda bisa akses sumber daya lain? Sebuah peran IAM dengan hak istimewa minimal yang dilampirkan ke fungsi.

Checklist kelulusan

  • Bisa definisikan nirserver dan bedakan dari server biasa.
  • Bisa jelaskan model event-driven dan layanan inti AWS.
  • Bisa tulis handler Lambda yang stateless.
  • Bisa jelaskan versioning, alias, dan infrastruktur-sebagai-kode.
  • Bisa jelaskan cara menguji & men-debug di lokal dan produksi.
  • Bisa sebut kapan serverless cocok dan kapan tidak.
