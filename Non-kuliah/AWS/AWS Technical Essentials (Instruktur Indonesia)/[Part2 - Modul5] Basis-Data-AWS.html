Basis data di AWS

Prasyarat
Penyimpanan di AWS
Dibuat
2026-10-11
Status
solid
Estimasi baca
30 menit

TL;DR

  • Basis data relasional menyimpan data dalam tabel (baris, kolom, relasi) dengan skema tetap; diakses lewat SQL.
  • Terlalu banyak pekerjaan? Pilih terkelola (Amazon RDS, Aurora) daripada tidak terkelola (self-manage di EC2).
  • Amazon RDS: tulis & kelola relasional; fitur kunci Multi-AZ (failover otomatis) dan snapshot/pencadangan otomatis.
  • Database dibuat khusus: DynamoDB (key-value), ElastiCache (in-memory), DocumentDB, Keyspaces, Neptune, Timestream, QLDB.
  • Strategi “basis data bebas”: satu layanan per fungsi, bukan satu basis data untuk semua.

Konsep inti

Basis data relasional dan SQL

Basis data relasional mengatur data ke dalam tabel; data di satu tabel dapat ditautkan ke tabel lain untuk membentuk hubungan. Baris (sering disebut catatan) berisi seluruh informasi satu entri, sedangkan kolom menggambarkan atributnya.

Penting karena tabel, baris, kolom, dan hubungan disebut skema logis, dan pada basis data relasional skema tersebut tetap — setelah berjalan, skema sulit diubah sehingga pemodelan data dilakukan lebih dulu. Anda berkomunikasi lewat kueri SQL, dan kekuatan sebenarnya muncul saat menarik data dari beberapa tabel sekaligus (join).

Miskonsepsi: skema relasional mudah diubah kapan saja. Tidak — skema bersifat tetap; perubahan skema setelah produksi berjalan mahal, jadi rancang skema di muka.

Manfaat basis data relasional

Empat manfaat utama: SQL kompleks (gabungkan beberapa tabel untuk memahami relasi), lebih sedikit redundansi (simpan data sekali, rujuk dari tabel lain), popularitas (dipakai sejak 1970-an, tenaga teknis sudah terbiasa), dan akurasi (integritas tinggi lewat prinsip atomisitas, konsistensi, isolasi, dan daya tahan atau ACID).

Penting karena sifat ACID dan popularitas membuatnya jadi pilihan default untuk banyak aplikasi vital, misalnya ERP, CRM, dan aplikasi niaga serta keuangan.

Miskonsepsi: relasional cocok untuk semua hal. Tidak — menjadi "perkakas gabungan" yang bisa banyak hal tetapi tidak terlalu unggul pada satu tugas; model data lain (key-value, dokumen, grafik) lebih tepat untuk beban tertentu.

RDBMS dan mesin yang didukung

Sistem manajemen basis data relasional (RDBMS) dipakai untuk membuat, memperbarui, dan mengelola basis data relasional. Contoh umum: MySQL, PostgreSQL, Oracle, Microsoft SQL Server, dan Amazon Aurora.

Penting karena pemilihan mesin menentukan fitur dan konfigurasi yang tersedia. Amazon RDS mendukung mesin komersial (Oracle, SQL Server), sumber terbuka (MySQL, PostgreSQL, MariaDB), dan cloud asli (Aurora).

Miskonsepsi: semua RDBMS identik. Tidak — fitur dan konfigurasi yang didukung berbeda per mesin, jadi pilih sesuai kebutuhan aplikasi.

Terkelola vs tidak terkelola

Layanan terkelola dan tidak terkelola ibarat kompromi antara kenyamanan dan kontrol, mirip model tanggung jawab bersama. Pada basis data tidak terkelola (mis. self-manage di Amazon EC2), AWS memelihara perangkat keras dan infrastruktur fisik, tetapi Anda tetap mengelola instans EC2, basis data pada host, pengoptimalan kueri, dan data pelanggan.

Pada basis data terkelola, layanan menyediakan penyiapan instans dan basis data, serta sistem untuk ketersediaan tinggi, skalabilitas, patching, dan cadangan. Anda masih bertanggung jawab atas penyetelan basis data, pengoptimalan kueri, dan keamanan data pelanggan — kenyamanan tertinggi dengan kontrol paling sedikit.

Miskonsepsi: terkelola berarti Anda lepas dari semua tanggung jawab. Tidak — penyetelan basis data, pengoptimalan kueri, dan keamanan data tetap di tangan Anda.

Amazon RDS dan instans basis data

Amazon Relational Database Service (Amazon RDS) adalah layanan basis data terkelola untuk membuat dan mengelola basis data relasional di cloud tanpa beban operasional tradisional — Anda melimpahkan penyediaan, patching, penskalaan, dan pemulihan.

Bagian komputasinya disebut instans basis data (DB instance) yang menjalankan mesin DB; di bawahnya ada instans EC2, tetapi dikelola lewat konsol RDS. Satu instans DB dapat berisi beberapa basis data bermesin sama, dan setiap basis data dapat berisi beberapa tabel.

Miskonsepsi: instans DB dikelola dari konsol Amazon EC2. Tidak — instans EC2 di bawahnya tetap dikelola melalui konsol Amazon RDS.

Penyimpanan Amazon RDS

Bagian penyimpanan instans DB memakai volume Amazon EBS untuk basis data dan penyimpanan log (MySQL, MariaDB, PostgreSQL, Oracle, SQL Server). Saat memakai Aurora, data disimpan dalam volume klaster: satu volume virtual berbasis SSD yang menyimpan salinan data di tiga Availability Zone.

Penting karena pemilihan jenis penyimpanan menyesuaikan kinerja dan biaya dengan beban kerja. RDS menyediakan tiga jenis: SSD Tujuan Umum (gp2, gp3), Provisioned IOPS SSD (io1), dan Magnetik (standar).

Miskonsepsi: Aurora memakai volume EBS per instans. Tidak — Aurora memakai volume klaster yang menyalin data ke tiga Availability Zone, bukan volume EBS biasa.

Amazon RDS di Amazon VPC

Saat membuat instans DB, Anda memilih Amazon VPC dan subnet untuk basis data. Kumpulan subnet ini disebut grup subnet DB, memuat setidaknya dua Availability Zone, dan subnetnya harus privat (tanpa rute ke gateway internet).

Penting karena isolasi ini memastikan instans DB dan datanya hanya dapat diakses oleh backend aplikasi. Akses dapat dibatasi lebih lanjut dengan ACL jaringan dan grup keamanan sebagai firewall berbutir halus.

Miskonsepsi: instans DB boleh berada di subnet publik agar mudah diakses. Tidak — subnet harus privat supaya hanya backend aplikasi yang bisa menghubungi basis data.

Cadangan data Amazon RDS

Ada dua opsi pencadangan: pencadangan otomatis (diaktifkan default, mencadangkan seluruh instans DB plus log transaksi, dengan retensi 0–35 hari) dan snapshot manual (dapat disimpan lebih dari 35 hari). Pencadangan otomatis memungkinkan point-in-time recovery.

Penting karena keduanya saling melengkapi; praktik yang dianjurkan adalah men-deploy kedua opsi. Menyetel retensi ke 0 hari akan menghentikan pencadangan otomatis sekaligus menghapus cadangan yang ada.

Miskonsepsi: retensi 0 hari hanya mematikan pencadangan baru. Tidak — menyetel 0 juga menghapus semua cadangan otomatis yang sudah ada.

Redundansi dengan Amazon RDS Multi-AZ

Deployment Multi-AZ membuat salinan basis data yang redundan di Availability Zone lain: salinan utama di satu subnet dan salinan siaga di subnet Availability Zone kedua. Data direplikasi secara sinkron ke siaga, dan salinan siaga tidak dikueri aplikasi.

Penting untuk ketersediaan tinggi: bila basis data utama kehilangan konektivitas, RDS memulai failover otomatis lewat nama DNS yang disediakan, mempromosikan basis data siaga ke peran utama dan mengalihkan kueri ke basis data utama yang baru.

Miskonsepsi: salinan siaga Multi-AZ bisa dipakai membaca untuk menambah kapasitas. Tidak — siaga bersifat pasif dan tidak dikueri; untuk menambah kapasitas baca gunakan read replica.

Keamanan Amazon RDS

Anda mengontrol akses ke sumber daya RDS. IAM menetapkan siapa yang boleh mengelola sumber daya (membuat, menjelaskan, memodifikasi, menghapus instans); grup keamanan mengontrol alamat IP atau instans EC2 yang boleh terhubung; enkripsi mengamankan instans dan snapshot saat diam; serta SSL/TLS melindungi koneksi ke instans.

Penting karena kontrol berlapis memastikan hanya instans backend dengan izin yang tepat yang dapat menyentuh basis data.

Miskonsepsi: instans DB baru bisa diakses lewat aturan grup keamanan bawaan. Tidak — saat pertama dibuat, semua akses basis data dicegah kecuali yang diizinkan aturan grup keamanan terkait.

Basis data yang dibuat khusus

AWS menawarkan lebih dari 15 mesin yang dibuat khusus untuk beragam model data: relasional, nilai kunci, dokumen, dalam memori, grafik, deret waktu, kolom lebar, dan buku besar. Pendekatan "satu ukuran untuk semua" dengan relasional untuk segala hal tidak lagi ideal.

Penting karena developer dapat memilih basis data sesuai kebutuhan aplikasi. Portofolio ini mendukung aplikasi berbasis data terdistribusi dengan skalabilitas tinggi dan membantu beralih dari basis data komersial yang penuh batasan.

Miskonsepsi: basis data khusus hanya "versi lebih baru" dari relasional. Tidak — masing-masing mengoptimalkan model data berbeda, bukan sekadar penerus relasional.

Layanan basis data khusus di AWS

Portofolio basis data AWS mencakup beberapa layanan dengan jenis dan kasus penggunaan berbeda:

LayananJenisKasus penggunaan
RDS, Aurora, RedshiftRelasionalERP, CRM, ecommerce
DynamoDBNilai kunciWeb, e-commerce, game
ElastiCacheDalam memoriCaching, sesi, skor

KeyspacesKolom lebarManajemen armada
NeptuneGrafikDeteksi penipuan

QLDBBuku besarRantai pasokan

Penting karena tiap layanan mengoptimalkan model datanya sendiri: ElastiCache menyimpan data dalam memori penuh terkelola (Redis, Memcached), MemoryDB menyediakan basis data in-memory tahan lama kompatibel Redis, DocumentDB adalah basis data dokumen terkelola penuh kompatibel API dengan MongoDB, Keyspaces kompatibel Apache Cassandra, Neptune adalah basis data grafik terkelola penuh, Timestream adalah deret waktu nirserver cepat, dan QLDB menyimpan riwayat perubahan yang dapat diverifikasi secara kriptografis.

Miskonsepsi: ElastiCache adalah basis data utama yang tahan lama. Tidak — ElastiCache adalah penyimpanan cache; untuk daya tahan gunakan MemoryDB atau basis data lain yang sesuai.

Amazon DynamoDB dan komponen intinya

Amazon DynamoDB adalah basis data NoSQL terkelola penuh yang memberi kinerja cepat dan dapat diprediksi dengan skalabilitas lancar. DynamoDB menyebarkan data dan lalu lintas ke cukup banyak server, menyimpan semua data di SSD, dan mereplikasinya otomatis di beberapa Availability Zone dalam satu Region.

Komponen intinya adalah tabel (kumpulan item), item (kumpulan atribut), dan atribut. DynamoDB memakai kunci primer untuk mengidentifikasi tiap item secara unik dan indeks sekunder untuk fleksibilitas kueri. Layanan ini cocok untuk aplikasi skala tinggi, nirserver, dan workload OLTP.

Miskonsepsi: DynamoDB butuh Anda menyediakan dan menambal server sendiri. Tidak — terkelola penuh; Anda tak mengurus penyediaan perangkat keras, replikasi, patch, atau skala klaster.

Keamanan DynamoDB

DynamoDB menyimpan data secara redundan pada beberapa perangkat di beberapa fasilitas dalam satu Region, mengenkripsi semua data saat diam memakai kunci di AWS KMS, dan mengandalkan IAM untuk mengautentikasi serta mengotorisasi akses.

Penting karena praktik terbaiknya mencakup penggunaan IAM role untuk kunci akses sementara, kondisi kebijakan IAM untuk kontrol terperinci (hak istimewa minimal), serta AWS CloudTrail untuk memantau penggunaan kunci terkelola AWS dan merekam aktivitas DynamoDB.

Miskonsepsi: enkripsi diam DynamoDB harus diaktifkan manual. Tidak — semua data pengguna yang tersimpan di DynamoDB dienkripsi sepenuhnya saat diam.

Memilih layanan basis data yang tepat

Pilih layanan basis data yang paling sesuai dengan pekerjaan agar mudah mengoptimalkan skala, kinerja, dan biaya. Relasional untuk aplikasi tradisional, ERP, CRM, dan ecommerce; nilai kunci untuk web lalu lintas tinggi dan game; dokumen untuk manajemen konten dan profil; grafik untuk deteksi penipuan dan rekomendasi; deret waktu untuk IoT dan telemetri.

Penting karena aplikasi modern tidak lagi didukung satu basis data. Aplikasi dipecah menjadi layanan lebih kecil, masing-masing dengan basis datanya sendiri — strategi basis data bebas yang memberi tiap basis data fungsi, kinerja, dan skala sesuai kebutuhan workload.

Miskonsepsi: satu basis data besar selalu lebih mudah dikelola. Tidak — memecah aplikasi dan memberi tiap layanan basis data terbaiknya menghilangkan gagasan "satu basis data untuk semua".

Kode

Kueri SQL dasar — memilih semua data dari satu tabel:

SELECT * FROM table_name;

-- gabungkan dua tabel untuk melihat relasinya
SELECT b.judul, p.tanggal
FROM buku AS b
JOIN penjualan AS p ON b.isbn = p.isbn;

AWS CLI — membuat instans Amazon RDS:

aws rds create-db-instance \
  --db-instance-identifier db-utama \
  --engine mysql \
  --db-instance-class db.t3.micro \
  --allocated-storage 20 \
  --multi-az

Apa yang berubah kalau X diubah: menambahkan --multi-az membuat salinan siaga di Availability Zone lain dan mengaktifkan failover otomatis, dengan biaya dua instans.

Latihan mandiri

1. Apa perbedaan tanggung jawab AWS dan pelanggan antara basis data yang dikelola sendiri di Amazon EC2 dan basis data terkelola seperti Amazon RDS?

Lihat jawaban

Pada EC2 (tidak terkelola), AWS memelihara perangkat keras dan infrastruktur fisik, tetapi pelanggan mengelola instans EC2, basis data pada host, pengoptimalan kueri, dan data. Pada RDS (terkelola), AWS menyediakan penyiapan instans dan basis data plus sistem untuk ketersediaan tinggi, skalabilitas, patching, dan cadangan; pelanggan masih menyetel basis data, mengoptimalkan kueri, dan mengamankan data.

2. Jelaskan bagaimana Amazon RDS Multi-AZ menangani kegagalan basis data utama.

Lihat jawaban

RDS menyimpan salinan utama di satu Availability Zone dan salinan siaga di Availability Zone lain, direplikasi secara sinkron. Bila utama kehilangan konektivitas, RDS memulai failover otomatis lewat nama DNS yang disediakan: basis data siaga dipromosikan ke peran utama dan kueri dialihkan ke basis data utama yang baru.

3. Sebuah aplikasi game butuh papan peringkat dengan akses sangat cepat dan sebuah sistem manajemen konten menyimpan dokumen kaya. Layanan basis data mana yang tepat untuk masing-masing?

Lihat jawaban

Papan peringkat: Amazon ElastiCache (basis data dalam memori, kasus penggunaan caching dan papan peringkat game). Manajemen konten: Amazon DocumentDB (basis data dokumen untuk manajemen konten, katalog, dan profil pengguna).

4. Kenapa DynamoDB cocok untuk aplikasi skala tinggi, dan apa komponen intinya?

Lihat jawaban

Karena DynamoDB terkelola penuh, menyebarkan data dan lalu lintas ke cukup banyak server, menyimpan data di SSD, dan mereplikasinya otomatis di beberapa Availability Zone sehingga memberi kinerja cepat dan dapat diprediksi. Komponen intinya: tabel (kumpulan item), item (kumpulan atribut), dan atribut, dengan kunci primer dan indeks sekunder.

5. Apa maksud strategi "basis data bebas" pada aplikasi modern?

Lihat jawaban

Aplikasi besar tidak lagi didukung satu basis data; aplikasi dipecah menjadi layanan lebih kecil yang masing-masing punya basis datanya sendiri, dipilih sesuai fungsionalitas, kinerja, dan skala workload-nya. Ini menggantikan gagasan satu basis data untuk semua.

Jebakan & FAQ

Apakah salinan siaga Multi-AZ dapat dipakai untuk membaca guna menambah kapasitas? Tidak. Salinan siaga bersifat pasif dan tidak dikueri aplikasi; ia disediakan untuk failover otomatis.

Apakah AWS menyediakan basis data relasional terkelola, atau harus self-manage di EC2? Keduanya tersedia. Yang tidak terkelola dijalankan di Amazon EC2; yang terkelola disediakan Amazon RDS (plus Aurora sebagai mesin cloud asli).

Bagaimana pencadangan otomatis dan snapshot manual berbeda? Pencadangan otomatis diaktifkan default, mencadangkan seluruh instans DB plus log transaksi, dan memungkinkan pemulihan titik waktu dengan retensi 0–35 hari. Snapshot manual dapat disimpan lebih dari 35 hari.

Kalau retensi pencadangan disetel 0 hari, apakah cadangan lama tetap aman? Tidak. Menyetel retensi ke 0 menghentikan pencadangan otomatis sekaligus menghapus semua cadangan otomatis yang ada.

Apakah Amazon Aurora memakai volume EBS biasa per instans? Tidak. Aurora menyimpan data dalam volume klaster, satu volume virtual berbasis SSD yang menyalin data ke tiga Availability Zone.

Apakah ElastiCache dapat menjadi basis data utama yang tahan lama? Tidak. ElastiCache adalah penyimpanan cache dalam memori; untuk basis data in-memory tahan lama gunakan MemoryDB for Redis.

Checklist kelulusan

  • Bisa jelaskan tabel, baris, kolom, dan skema logis relasional.
  • Bisa sebut contoh RDBMS dan peran kueri SQL dengan join.
  • Bisa bedakan basis data terkelola dan tidak terkelola.
  • Bisa jelaskan peran Amazon RDS dan instans basis data.
  • Bisa jelaskan penyimpanan RDS (EBS) dan volume klaster Aurora.
  • Bisa bedakan pencadangan otomatis dan snapshot manual.
  • Bisa jelaskan cara kerja Multi-AZ dan failover otomatis.
  • Bisa sebut kontrol keamanan Amazon RDS (IAM, grup keamanan, enkripsi).
  • Bisa petakan jenis basis data ke layanan AWS yang tepat.
  • Bisa jelaskan komponen inti dan keamanan DynamoDB.
  • Bisa jelaskan strategi "basis data bebas".
