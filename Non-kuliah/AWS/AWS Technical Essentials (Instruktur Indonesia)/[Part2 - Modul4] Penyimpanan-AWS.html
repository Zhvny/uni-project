Penyimpanan di AWS

Prasyarat
Komputasi AWS
Dibuat
2026-10-11
Status
solid
Estimasi baca
30 menit

TL;DR

  • Tiga kategori penyimpanan: file (hierarki), blok (potongan berukuran tetap beralamat), objek (bucket datar).
  • Penyimpanan file: Amazon EFS (elastis, Multi-AZ) dan Amazon FSx (NetApp ONTAP, OpenZFS, Windows, Lustre).
  • Penyimpanan blok: EC2 instance store (sementara) dan Amazon EBS (persisten, dipasang 1-ke-1, di-snapshot ke S3).
  • Penyimpanan objek: Amazon S3 — bucket + key + Region, privat secara default, punya kelas penyimpanan dan versioning.
  • Otomatiskan penurunan biaya dengan lifecycle: transisi antar kelas dan penghapusan terjadwal.

Konsep inti

Tiga kategori penyimpanan

Layanan penyimpanan AWS dibagi tiga kategori: penyimpanan file (data sebagai file dalam hierarki folder), penyimpanan blok (data sebagai blok berukuran tetap yang tiap bloknya punya alamat sendiri), dan penyimpanan objek (data sebagai objek di dalam bucket dengan struktur datar).

Penting karena tiap kategori dioptimalkan untuk beban kerja berbeda. Penyimpanan blok unggul untuk operasi latensi rendah dan I/O intens; penyimpanan objek unggul untuk skala besar dan data tak terstruktur.

Miskonsepsi: ketiganya bisa saling menggantikan. Tidak — "bucket datar" S3 tidak cocok menjadi sistem file, dan EBS tidak bisa diakses dari web secara langsung.

Penyimpanan file: Amazon EFS

Amazon Elastic File System (Amazon EFS) adalah sistem file sederhana yang otomatis tumbuh dan menyusut saat file ditambah atau dihapus. Tidak perlu menyediakan kapasitas maupun kinerja. Puluhan hingga ribuan instans komputasi bisa terhubung bersamaan dengan kinerja konsisten per instans.

Penting karena cocok untuk akses terpusat dan berbagi antar-host. Kelas penyimpanannya: EFS Standard dan Standard-IA (Multi-AZ, ketahanan dan ketersediaan tertinggi), serta EFS One Zone dan One Zone-IA (data dalam satu Availability Zone, lebih hemat).

Miskonsepsi: EFS perlu disediakan kapasitasnya di awal. Tidak — EFS elastis; Anda hanya membayar penyimpanan yang benar-benar dipakai.

Penyimpanan file: Amazon FSx

Amazon FSx adalah layanan terkelola penuh untuk sistem file pihak ketiga berkinerja tinggi. Pilihan sistem file: NetApp ONTAP, OpenZFS, Windows File Server (protokol SMB), dan Lustre (throughput hingga 1+ TB/dtk, IOPS jutaan, sering dikaitkan ke repositori data Amazon S3).

Penting karena FSx mempertahankan kompatibilitas asli dengan sistem file yang sudah dipakai on-premises, sehingga migrasi tidak perlu mengubah kode aplikasi. FSx mengotomatisasi penyediaan perangkat keras, konfigurasi perangkat lunak, patching, dan pencadangan.

Miskonsepsi: FSx adalah satu produk tunggal. Tidak — FSx adalah keluarga layanan, dan Anda memilih salah satu dari empat sistem file.

Penyimpanan blok: EC2 instance store

Amazon EC2 instance store menyediakan penyimpanan tingkat blok sementara yang terpasang fisik pada komputer host instans. Siklus hidupnya terikat pada instans: menghapus instans berarti data ikut terhapus.

Penting untuk kecepatan dan data yang tidak perlu bertahan lama, misalnya buffer, cache, dan data scratch. Cocok juga bagi aplikasi yang mereplikasi data ke instans lain, seperti klaster Hadoop, karena volume lokal cepat plus replikasi memberi performa tinggi.

Miskonsepsi: instance store aman untuk data penting. Tidak — bersifat sementara; jangan pakai untuk data persisten yang harus bertahan saat instans berhenti atau gagal.

Penyimpanan blok: Amazon EBS

Amazon Elastic Block Store (Amazon EBS) adalah penyimpanan tingkat blok yang dipasang ke instans EC2. Penyimpanan yang dipasang ini disebut volume EBS, analog drive eksternal: dapat dilepas dan dipasang ulang di Availability Zone yang sama, terpisah dari komputasi, berukuran terbatas, dan umumnya berelasi satu-ke-satu dengan instans.

Penting karena volume EBS bertahan saat instans berhenti, diakhiri, atau perangkat keras gagal. Fitur kuncinya: direplikasi otomatis dalam Availability Zone-nya (ketersediaan tinggi), mendukung enkripsi, dan dapat dimodifikasi tanpa menghentikan instans.

Miskonsepsi: satu volume EBS bisa dipasang ke banyak instans sekaligus. Umumnya tidak — hampir semua volume berelasi 1-ke-1; multipasang hanya untuk volume SSD io1/io2 di Availability Zone yang sama.

Tipe volume EBS

Volume EBS dibagi dua kategori: solid-state drive (SSD) untuk beban transaksional dengan operasi baca/tulis sering berukuran I/O kecil, dan hard disk drive (HDD) untuk beban streaming besar yang membutuhkan throughput tinggi.

Penting karena pemilihan tipe menentukan biaya dan kinerja. Ukuran volume maksimum EBS saat ini mencapai 64 tebibita (TiB) untuk tipe tertentu.

KategoriCocok untuk
SSD tujuan umum (gp3, gp2)Keseimbangan harga dan kinerja
SSD IOPS tersedia (io1, io2)Beban peka latensi
HDD throughput (st1)Beban sering diakses, throughput
HDD dingin (sc1)Beban jarang diakses, biaya rendah

Miskonsepsi: semua volume EBS bisa diskalakan sama. Tidak — batas ukuran, IOPS, dan throughput berbeda per tipe volume.

Snapshot Amazon EBS

Snapshot adalah cadangan volume EBS yang bersifat tambahan (incremental): hanya blok yang berubah sejak snapshot terakhir yang disimpan. Jika data 10 GB di volume dan 2 GB berubah, hanya 2 GB itu yang ditulis.

Penting sebagai pengaman terhadap kehilangan data. Snapshot disimpan redundant di beberapa Availability Zone menggunakan Amazon S3, tetapi dikelola lewat konsol Amazon EBS — Anda tidak perlu menyentuh Amazon S3 langsung. Snapshot dapat dipakai membuat volume baru yang identik.

Miskonsepsi: snapshot menyimpan seluruh volume setiap kali. Tidak — snapshot bersifat tambahan, sehingga hemat ruang dan biaya.

Penyimpanan objek: konsep Amazon S3

Amazon Simple Storage Service (Amazon S3) adalah penyimpanan objek mandiri yang tidak terikat komputasi dan dapat diakses dari mana saja di web. Objek adalah file ditambah metadata, disimpan dalam struktur datar di dalam kontainer bernama bucket.

Penting karena S3 memberikan skalabilitas tidak terbatas, durabilitas tinggi, dan efektivitas biaya. Objek diidentifikasi unik oleh kombinasi nama bucket, key, dan ID versi. Nama bucket harus unik di semua akun AWS dalam satu partisi (3–63 karakter, huruf kecil, angka, titik, tanda hubung). S3 tidak punya hierarki asli, tetapi konsol memberi kesan folder lewat awalan (prefix) dan pembatas /.

Miskonsepsi: folder di S3 adalah struktur nyata. Tidak — S3 hanya bucket dan objek; folder hanyalah ilusi dari awalan nama key.

Keamanan Amazon S3

Semua sumber daya S3 — bucket, folder, dan objek — privat secara default; hanya akun yang membuatnya yang bisa melihat. Akses diberikan lewat kebijakan akses. S3 juga otomatis mengenkripsi semua objek saat diunggah, dengan enkripsi sisi server berkunci yang dikelola S3 sebagai tingkat dasar tanpa biaya tambahan.

Penting karena dua fitur utama mengatur izin: kebijakan IAM (dilampirkan ke sumber daya atau ke pengguna/grup/peran) dan kebijakan bucket S3 (format JSON, hanya bisa dilampirkan ke bucket, berlaku untuk objek di dalamnya).

Miskonsepsi: objek S3 publik sejak awal. Tidak — semuanya privat secara default; membuka akses harus dipilih secara sadar lewat kebijakan.

Kelas penyimpanan Amazon S3

Ketika objek diunggah tanpa menentukan kelas, objek masuk ke kelas default (S3 Standard). Kelas penyimpanan memungkinkan Anda menurunkan tingkatan penyimpanan saat pola akses data berubah, misalnya foto lama yang jarang dibuka.

Penting karena biaya penyimpanan turun seiring jarangnya akses, dengan konsekuensi waktu pengambilan yang lebih lama atau ketersediaan AZ yang lebih sedikit.

KelasCocok untuk
S3 StandardSerba guna, akses sering
S3 Intelligent-TieringPola akses tak menentu
S3 Standard-IAJarang diakses, akses cepat
S3 One Zone-IASatu AZ, biaya lebih rendah
S3 Glacier Instant RetrievalArsip, ambil milidetik
S3 Glacier Flexible RetrievalArsip, ambil 1–5 menit
S3 Glacier Deep ArchiveRetensi 7 tahun atau lebih
S3 on OutpostsData lokal on-premise

Miskonsepsi: kelas termurah selalu terbaik. Tidak — S3 Glacier Deep Archive punya waktu pengambilan default 12 jam, tidak cocok untuk data yang kadang harus segera diambil.

Versioning Amazon S3

Tanpa versioning, mengunggah objek dengan nama yang sama akan menimpa objek aslinya. Versioning menyimpan beberapa versi dari satu objek dalam bucket yang sama; saat diaktifkan, S3 otomatis membuat ID versi unik.

Penting untuk memulihkan objek dari penghapusan atau penimpaan tak sengaja. Penghapusan tidak langsung menghapus permanen — S3 menaruh penanda hapus (delete marker) yang bisa dihapus untuk memulihkan objek. Status bucket: tanpa versi (default), versioning-aktif (tidak bisa balik ke tanpa versi, hanya ditangguhkan), dan ditangguhkan (objek baru tanpa versi, objek lama tetap berversi).

Miskonsepsi: versioning gratis. Tidak — biaya penyimpanan dikenakan untuk semua versi, jadi hapus versi lama yang tak diperlukan.

Siklus hidup (lifecycle) Amazon S3

Konfigurasi siklus hidup mengotomatisasi dua jenis tindakan pada objek atau grup objek: transisi (kapan objek pindah ke kelas penyimpanan lain) dan kedaluwarsa (kapan objek dihapus permanen).

Penting agar Anda tidak perlu memindahkan objek secara manual. Contoh: transisi ke S3 Standard-IA 30 hari setelah dibuat, atau arsipkan ke S3 Glacier Deep Archive setelah satu tahun. Kandidat yang baik: log berkala dan data yang frekuensi aksesnya berubah.

Miskonsepsi: lifecycle hanya untuk menghapus. Tidak — tindakan transisinya justru alat utama untuk menekan biaya penyimpanan.

Memilih layanan penyimpanan

Pilihan bergantung pada sifat data. EBS untuk data yang sering berubah dan harus bertahan melewati penghentian instans; S3 untuk data yang jarang berubah dan butuh skala besar; EFS untuk sistem file bersama cloud-native; FSx untuk kompatibilitas sistem file pihak ketiga.

Penting karena kesalahan memilih menaikkan biaya dan risiko. EBS adalah penyimpanan blok yang dibayar sesuai yang disediakan (provisioned), sedangkan S3 adalah penyimpanan objek yang dibayar sesuai pemakaian dan tidak terpasang ke komputasi.

Miskonsepsi: EFS bisa menggantikan EBS untuk semua kasus. Tidak — EFS adalah penyimpanan file yang diakses bersama, sedangkan EBS adalah blok yang umumnya dipasang satu-ke-satu ke instans.

Kode

Konfigurasi lifecycle S3 (JSON) — transisi ke STANDARD_IA setelah 30 hari:

{
  "Rules": [
    {
      "ID": "arsip-foto",
      "Status": "Enabled",
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" }
      ],
      "Expiration": { "Days": 365 }
    }
  ]
}

AWS CLI — menerapkan konfigurasi dan mengunggah objek:

# terapkan lifecycle ke bucket
aws s3api put-bucket-lifecycle-configuration \
  --bucket my-bucket \
  --lifecycle-configuration file://lifecycle.json

# unggah objek ke bucket
aws s3 cp photo.jpg s3://my-bucket/foto/photo.jpg

Apa yang berubah kalau X diubah: menaikkan nilai Days pada Transitions menunda perpindahan ke kelas yang lebih murah, sehingga biaya penyimpanan aktif bertahan lebih lama.

Latihan mandiri

1. Sebutkan tiga kategori penyimpanan AWS dan satu ciri pembeda tiap kategori.

Lihat jawaban

File — data sebagai file dalam hierarki folder. Blok — data sebagai potongan berukuran tetap yang tiap bloknya beralamat. Objek — data sebagai objek di dalam bucket berstruktur datar.

2. Anda perlu penyimpanan yang bertahan saat instans EC2 dihentikan, dapat di-snapshot, dan umumnya dipasang ke satu instans. Layanan dan kategori mana yang tepat?

Lihat jawaban

Amazon EBS, kategori penyimpanan blok. Volume EBS persisten (bertahan melewati penghentian/pengakhiran instans), mendukung snapshot, dan umumnya berelasi 1-ke-1 dengan instans EC2.

3. Kenapa snapshot EBS lebih hemat ruang daripada menyalin seluruh volume setiap kali?

Lihat jawaban

Karena snapshot bersifat tambahan: hanya blok yang berubah sejak snapshot terakhir yang disimpan. Contoh, dari data 10 GB hanya 2 GB yang berubah, jadi hanya 2 GB itu yang ditulis.

4. Data arsip diakses sekitar satu kali per tahun dan harus disimpan tujuh tahun untuk kepatuhan. Kelas penyimpanan S3 mana yang paling hemat, dan apa konsekuensinya?

Lihat jawaban

S3 Glacier Deep Archive — kelas penyimpanan S3 dengan biaya terendah. Konsekuensinya waktu pengambilan default 12 jam, cocok untuk retensi jangka panjang, bukan untuk data yang butuh akses cepat.

Jebakan & FAQ

Apakah S3 punya hierarki folder sungguhan? Tidak. S3 hanya menyimpan bucket dan objek dalam struktur datar; konsol menyiratkan folder lewat awalan nama key dan pembatas /.

Apa beda kebijakan IAM dan kebijakan bucket S3? Kebijakan IAM dapat dilampirkan ke sumber daya maupun ke pengguna, grup, dan peran; kebijakan bucket S3 hanya dilampirkan ke bucket dan berlaku untuk objek di dalamnya. Pakai kebijakan IAM bila ingin semua kebijakan terpusat di satu lokasi, dan kebijakan bucket untuk akses lintas akun yang sederhana.

Kalau versioning diaktifkan, bisakah dikembalikan ke tanpa versi? Tidak. Bucket yang pernah diaktifkan versioning tidak bisa kembali ke status tanpa versi; paling jauh Anda menangguhkan versioning.

Apakah penghapusan objek di bucket berversi langsung permanen? Tidak. S3 menaruh penanda hapus; objek bisa dipulihkan dengan menghapus penanda tersebut.

Kapan pakai Amazon EFS, bukan Amazon EBS? Saat butuh sistem file bersama yang diakses banyak instans komputasi sekaligus dan tumbuh-menyusut otomatis. EBS adalah blok yang umumnya dipasang ke satu instans.

Apakah semua volume EBS bisa dipasang ke beberapa instans? Tidak. Multipasang hanya didukung volume SSD Provisioned IOPS (io1 atau io2), dan semua instans harus berada di Availability Zone yang sama.

Checklist kelulusan

  • Bisa sebut tiga kategori penyimpanan dan ciri pembedanya.
  • Bisa jelaskan kelas penyimpanan Amazon EFS (Standard vs One Zone).
  • Bisa sebut empat sistem file di Amazon FSx.
  • Bisa bedakan instance store (sementara) dan volume EBS (persisten).
  • Bisa bedakan tujuan volume SSD dan HDD EBS.
  • Bisa jelaskan kenapa snapshot EBS bersifat tambahan.
  • Bisa jelaskan konsep bucket, key, dan Region di Amazon S3.
  • Bisa bedakan kebijakan IAM dan kebijakan bucket S3.
  • Bisa memilih kelas penyimpanan S3 sesuai pola akses data.
  • Bisa jelaskan versioning dan tindakan lifecycle (transisi, kedaluwarsa).
